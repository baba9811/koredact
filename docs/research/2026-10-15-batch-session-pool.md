# 배치 세션 재사용과 동적 배분

요구사항: `predict_many`/`mask_many`의 공개 시그니처·출력·입력 순서·오류 계약 유지. 배치 호출마다 반복되던
추가 세션 적재·해제 제거. 0.4.0 측정(4 vCPU, `threads=1`, fp32): 중간 길이 3건 순차 0.49초, `workers=2`
1.52초, `workers=4` 1.63초. fp32 32건 실행은 추가 세션 적재 중 OOM 종료.

## 공식 근거와 적용

- [ONNX Runtime `InferenceSession::Run`](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/session/inference_session.h):
  "Multiple threads are allowed to run this function; hence its thread-safe." 명시. 실행 제공자가
  `ConcurrentRunSupported() == false`이면 ORT 내부에서 그래프 실행 구간 잠금
  (`is_concurrent_run_supported_`, [inference_session.cc](https://github.com/microsoft/onnxruntime/blob/main/onnxruntime/core/session/inference_session.cc)).
- [ort 2.0.0-rc.13 `Session`](https://docs.rs/ort/2.0.0-rc.13/ort/session/struct.Session.html):
  `Session::run`의 `&mut self` 요구([v2.0.0-rc.10 변경](https://github.com/pykeio/ort/releases/tag/v2.0.0-rc.10),
  설치 crate `src/session/mod.rs:236` 확인). 사유: 일부 ORT 내부 요소(실행 제공자 할당자·통계 추적기)의 스레드
  비안전성. 동시 추론에는 스레드별 세션 권장. 적용: 안전한 Rust에서 세션 1개 공유 시 `Mutex` 필요, 결과적으로
  추론 직렬화. `unsafe`로 만든 `&mut` 별칭은 정의되지 않은 동작. 워커별 세션 1개 생성 후 재사용.
- [ORT 스레드 관리](https://onnxruntime.ai/docs/performance/tune-performance/threading.html):
  세션별 intra-op 스레드 풀, 세션 스레드 풀 간 경합 언급. 적용: `workers × threads`를 CPU 할당량 이하로 안내.
  전역 스레드 풀 도입은 제외.
- [ORT 메모리 관리](https://onnxruntime.ai/docs/performance/tune-performance/memory.html):
  공유 arena 할당자로 여러 세션의 메모리 절감 가능. 이번 범위 제외, 메모리는 세션 수에 비례.
- [Ciorba et al., OpenMP Loop Scheduling Revisited, arXiv:1809.03188](https://arxiv.org/abs/1809.03188):
  동적 자기 배분(self-scheduling)의 목표는 부하 불균형과 배분 비용 최소화. 적용: 입력 비용이 400자 창 수에
  비례해 고르지 않으므로 정적 연속 분할 대신 입력 단위 원자적 카운터 배분. 창 하나가 수십~수백 ms라 입력당
  원자 연산 비용 무시 가능.

## 구현과 검증 범위

- `Masker`에 추가 세션 풀 보관. 같은 번들·`threads`·장치 선호로 첫 배치 호출에서 적재, 이후 호출 재사용.
  필요 수 `min(workers, 입력 수) - 1`, 부족분만 추가 적재. 최대 사용 수 유지(축소 없음). 적재 실패 시 기존
  세션만으로 처리.
- 배치 호출마다 치환 문자열 복사. 호출 사이 `set_mask_tokens` 변경 반영.
- 동적 배분: 호출 스레드와 워커 스레드가 공유 원자 카운터에서 다음 입력 번호를 가져감. 결과는 번호 위치에
  저장, 입력 순서 유지.
- 오류 계약: 번호는 증가 순서로만 배분, 첫 실패 관측 후 새 배분만 중단. 가장 앞선 실패 입력까지의 번호는 모두
  처리 완료 후 그 오류 반환. 정적 연속 분할(구간별 첫 오류에서 중단)과 같은 오류. 워커 스레드 패닉은 해당
  입력의 `batch worker panicked` 실패로 기록, 완료 결과 유지 후 같은 규칙 적용. 패닉한 추가 세션은 풀에서
  제거, 다음 호출에서 새로 적재. 스레드 생성 실패 시 생성된 워커와 호출 스레드로 처리.
- `workers=1`: 추가 세션 적재 없이 호출 스레드에서 순차 처리. 공개 Rust·Python 시그니처, 스팬 출력,
  `workers == 0` 오류 유지.
- 알려진 특성
  - 가속기에서 추가 세션마다 독립적인 CPU 대체 가능. 입력별 처리 세션이 호출마다 달라 가속기·CPU 세션이
    섞이면 점수 미세 차이 가능. CPU 전용 결과는 동일.
  - 추가 세션의 CPU 대체 상태도 `Masker` 수명 동안 유지. 가속기 실패 후 CPU 재적재까지 실패한 세션은 기본
    세션과 같이 이후 호출에서도 오류 반환.
  - 호출 스레드의 패닉은 그대로 전파. 이때 세션 풀 유실, 다음 배치 호출에서 재적재.
- 범위 제외: 세션 1개의 `Mutex` 공유, `unsafe` 공유, 공유 arena·사전 패킹 가중치 공유, 세션 해제 API,
  CPU 코어 수 자동 감지, `DEFAULT_REPO` 변경, 버전 변경(릴리스 시 별도 결정).

## 로컬 검증 결과

- Rust: `cargo test --release --no-default-features --features load-dynamic`에서 단위 24개·디코더 벡터 1개
  통과. ORT 필요 검사 3개(`--lib -- --ignored`)는 ONNX Runtime 1.29.0 동적 라이브러리로 통과.
  - 세션 재사용: 첫 호출 세션의 `Arc`를 보유한 채 이후 호출과 포인터 동일성 비교. `workers` 3, 1, 2, 99 순서
    호출 후에도 기존 세션 유지, 세션 수는 최대 사용 수까지만 증가. 오류 반환 후에도 세션 유지. 패닉한 추가
    세션은 제거 후 다음 호출에서 새 세션 적재.
  - 오류 계약: 앞선 실패 입력에 지연을 주입한 200회 반복으로 가장 앞선 실패 입력의 오류 확인. 테스트 30회 반복
    실행 실패 0건. 진행 중 결과를 버리는 변형 코드는 같은 검사에서 실패 확인.
  - 워커 패닉 순서: 워커가 앞 번호 완료 후 더 뒤 번호에서 패닉, 그 사이 번호에서 호출 스레드 오류인 순서를
    동기화로 강제. 호출 스레드 오류 반환 확인. 패닉을 잡지 않거나 완료 결과를 버리는 변형 코드는 실패 확인.
    검사 대기는 10초 기한, 워커 미기동 시 무한 대기 대신 실패.
- Python: 로컬 빌드 휠로 smoke·`runtime_options.py` 통과(ONNX Runtime 1.31.0). Python API에는 치환 문자열 변경
  메서드가 없어 호출 사이 변경은 Rust 검사로 확인, Python은 `Masker`별 치환 문자열 분리 확인.
- 기존 `failed_accelerator_run_retries_same_input_on_cpu`: ONNX Runtime 1.31.0 동적 라이브러리에서 NaN 주입
  단계 실패, 변경 전 커밋 c5697e7도 동일. 1.29.0에서는 통과. 런타임 버전 차이로 별도 확인 필요.
- macOS 27.0.1 Command Line Tools 27 링커로 만든 확장 모듈은 LINKEDIT 문자열 풀 4바이트 정렬로 dyld 적재 거부.
  로컬 검증 휠만 `-C link-arg=-Wl,-fixup_chains`로 빌드. 저장소 빌드 설정은 미변경.

성능 측정: 합성 텍스트(가짜 개인정보 문장), `threads=1`, `device="cpu"`, ONNX Runtime 1.29.0, 구성별 별도
프로세스, `predict_many` 연속 5회 호출. 0.4.0은 PyPI 휠, 변경본은 같은 소스의 로컬 빌드 휠. 모든 호출에서 순차
`predict`와 스팬·점수 동일. 단위: 초. 이후 호출은 2~5회차 중앙값, 피크 RSS는 프로세스 최대값(MB).
표의 변경본은 워커 패닉 처리 추가 전 빌드. 추가 후 빌드와 macOS INT8 32건·4 워커 교차 3회 비교에서 이후 호출
중앙값 0.39초·0.36초, 잡음 범위 내 동일.
